FlyingScotman/trading-desk-monitor#535. Связанные: FlyingScotman/trading-desk-monitor#557 (PnL сделок дня),

FlyingScotman/trading-desk-monitor#548 (сервисы адаптера), FlyingScotman/trading-desk-monitor#553 (владельцу — кнопки,
не командная строка). Ссылки на код — по ветке с PnL сделок дня (коммит `1d26be7`).

Публичный репозиторий: здесь только общие названия (ADR-008). Что именно умеет сервис сделок организации и как
адаптер его спрашивает — в приватном адаптере (`tasks/A12_trades_history.md`).

## 1. Коротко

Пересчёт уже есть. Любой прогон даты D применяет сделки D, если они лежат в базе, а подпись входов прогона их учитывает.
Как только в базе появляются сделки прошлой даты, эта дата сама становится «устаревшей»: свежие даты пересчитывает шаг
eod автопилота, старые — шаг backfill. Чего нет — **сделок прошлых дат в базе**: фид «сделки дня» по расписанию
спрашивает только сегодняшний день. Поэтому новый воркер только догружает сделки. Он идёт от свежих дат к старым, по
одной дате, через тот же фид адаптера с параметром `date`, и ведёт отметки по датам. Пересчитывают существующие шаги
автопилота. Подъём `VALUATION_VERSION` не нужен. Пересчитываются только даты, где сделки по облигациям действительно
изменили входы.

## 2. Что есть сейчас

### 2.1 Сделки в прогоне и компонента `new_trades`

- Прогон любой даты D (`cli.eod_run`, `backend/src/desk/cli.py:209`) берёт позиции `store.positions_for` и проводит
  их через `trades.intraday_inputs` (`cli.py:299`; `backend/src/desk/trades.py:450`). Внутри `apply_intraday`
  (`trades.py:272`) сделки D берутся из базы (`store.dataset_rows(con, "trades", on)`, набор `trades`, поток: дата
  берётся только своя, не переносится).
- Книга с отчётом позиций за D: позиции строго по отчёту. Позиция начала дня — предыдущий набор
  (`positions_for(on - 1)`). Сделки D дают только PnL. Расхождение отчёта и «начало дня + сделки» отмечается
  `x.trades_report_gap`. Книга без отчёта за D: её набор плюс сделки дней после отчёта (не старше
  `MAX_HISTORY_DAYS = 7`, `trades.py:110`) плюс сделки D.
- PnL изменённой позиции — PnL позиции начала дня (полная раскладка flash) плюс `new_trades`
  (`backend/src/desk/pnl/new_trades.py`, вызов `cli.py:355`). Компонента попадает в `pnl` строки прогона
  (`pnl/flash.py:353`, `pnl/direct.py:97`, `publish/desk_run.py:57` `PNL_KEYS`) и в группу «trading» сводки
  (`publish/summary.py:65`). История PnL и «PnL за период» (`api/pnl_period.py:46`) суммируют компоненты основных
  прогонов дат. Поэтому пересчитанная дата появляется там сама.
- Подпись входов: `private_inputs_hash` заменяется хешем от `[хеш позиций, применённые сделки, сделки прошлых дней,
  хеш набора начала дня, history_cut]` (`trades.py:445`). Если у даты нет сделок, сделки не по облигациям или все
  пропущены, вход возвращается без изменений (`trades.py:334`, `:343`): хеш прежний, дата не пересчитывается.
- PnL даты D не читает прогон D−1. Позиции D переоцениваются на рынке D−1 (`cli.py:345–355`). От прошлых прогонов
  зависят только перенесённые спреды model price (`store.carried_spreads`, `store/__init__.py:634`).

### 2.2 Заморозка и как дата становится устаревшей

- Прогон после `complete`/`failed` не меняется: триггеры `run_frozen` и `run_log_frozen`
  (`store/migrations/0001_init.sql:137–152`). Пересчёт — всегда **новый** прогон. Основной прогон даты — последний
  complete EOD (`store.DEFAULT_RUNS`, `store/__init__.py:567`). Старый прогон остаётся в базе.
- `backfill.plan` (`backend/src/desk/backfill.py:221`) для каждой даты с позициями и закрытием хаба сравнивает
  основной прогон с текущими входами. Хеш берётся из `trades.intraday_inputs` (`backfill.py:251`). Если он другой,
  дата получает статус `todo` с причиной «private inputs changed» (`:256`). Подпись даты `Day.sig` (`:259`) включает
  хеш, поэтому дата, проблемная на старых входах (`failed`, `MAX_ATTEMPTS = 2`, `:99`), с новыми сделками пробуется
  снова. `backfill.run` (`:405`) идёт от старых дат к новым (из-за перенесённых спредов), по одной, в пределах
  `backfill_budget_s` за цикл (600 с, `settings.py:319`), после всех остальных шагов автопилота
  (`autopilot.py:476`).
- Шаг eod автопилота (окно `WINDOW_DAYS = 14`, не больше `MAX_EOD_DATES = 10` дат, `autopilot.py:152–153`) по тому же
  признаку пересчитывает свежие даты (`autopilot.py:1049–1053`). Сегодняшние INTRADAY- и утренние прогоны — тоже по
  хешу (`autopilot.py:1192`, `:1293`).
- `recompute.after_inputs` (`backend/src/desk/recompute.py`) после приёма файлов фида сразу пересчитывает EOD даты,
  если её закрытие лежит в кэше (`recompute.py:46–75`), и сегодняшние прогоны.

### 2.3 Откуда берутся сделки

- Сделки приходят только файлами набора `trades` через обычный путь приёма. Фид «сделки дня» помощника сервисов
  адаптера (FEED с `books: true`, FlyingScotman/trading-desk-monitor#557) по расписанию вызывается без даты, то есть
  за сегодня.
- Протокол уже позволяет передать дату. `Service.run_feed(feed_id, day)` (`adapter_services.py:691`), маршрут
  `POST /api/v1/adapter-services/feeds/{id}/run` с полем `date` (`api/adapter_services_routes.py:83`), запрос
  `feed` с `date` (`adapter_services.py:1007`). Книги владельца на дату — `owner_books(con, D)`
  (`adapter_services.py:265`). Файлы идут через `scan.ingest_feed` без окна давности (`inbox/scan.py:997`, без
  `lookback`), затем `recompute.after_inputs` (`adapter_services.py:1176`).
- Повторная выгрузка той же даты с тем же содержимым новой ревизии не даёт (`unit_hash`, `inbox/scan.py:25`), и
  хеш не меняется. Изменённая выгрузка (поздние бронирования, отмены, новые версии сделок) даёт новую ревизию
  (`full_snapshot` по книге, порядок по `report_ts`, 08 §10 `trades`), и даты пересчитываются.
- Чего не хватает:
  1. никто не спрашивает фид за прошлые даты;
  2. ручной запуск с датой пишет состояние в запись самого фида (`_record(... date=day)`, `adapter_services.py:962`).
     Если такой запуск завершился ошибкой, повтор по расписанию возьмёт эту прошлую дату вместо сегодняшней
     (`adapter_services.py:931`), а пауза «нужен вход» остановит и сегодняшний фид;
  3. по ответу фида монитор не отличает «за дату сделок не было» от «книги сервиса не сопоставлены с книгами монитора»:
     в обоих случаях файл без единиц приёма;
  4. монитор не знает, какой фид умеет отвечать за прошлые даты.
- Последний срез дня. Фид идёт по расписанию в окне «с … до …», поэтому сделки D в базе — срез последнего запуска
  в день D, без вечерних сделок и поздних бронирований. Выгрузка D, сделанная после конца D, даёт срез на конец дня.

### 2.4 Интерфейс

Настройки → «История прогонов» (`prototypes/settings.html:779`, `:1123`, данные `GET /api/v1/backfill/status`,

## 3. Проект

### 3.1 Где живёт воркер

Отдельного потока и нового фреймворка нет. Воркер — ещё одна ветка в рабочем цикле `adapter_services.Service`.
Помощник адаптера и так вызывается по одному процессу за раз, под `HELPER_LOCK`, а приём файлов ждёт блокировку цикла
автопилота. Вызывать помощника из шага автопилота нельзя: автопилот держит блокировку цикла, а приём файлов фида ждёт
её же (взаимная блокировка).

- Новый модуль `backend/src/desk/trades_history.py` без потоков и без вызовов помощника. В нём: кандидаты, выбор
  следующей даты, разбор ответа в отметку, файл состояния, сводка для экрана.
- `Service._step` (`adapter_services.py:542`): после заданий владельца, «Запустить сейчас» и фидов по расписанию.
  Если ничего не готово к запуску и прошло `HISTORY_GAP_S` с прошлой догрузки, воркер берёт одну дату
  (`trades_history.next_date`) и вызывает `_history_fetch(st, f, day)`.
- `_history_fetch` использует то же, что `_feed`: книги владельца на D (`owner_books(con, D)`), обрезку запроса по
  пределам, `_call(..., "feed", {"feed", "date", "book"})`, проверку ответа `clean_feed_result`, приём `_ingest`.
  Отличия от `_feed`:
  1. состояние пишется в файл догрузки (§3.5), а не в `runs[<фид>]`, поэтому расписание, повторы и пауза
     сегодняшнего фида от догрузки не зависят;
  2. `_ingest(..., recompute=False)`: после приёма не вызывается `recompute.after_inputs`, блокировка цикла держится
     только на время приёма файла. Пересчитывают шаги eod и backfill автопилота в своём бюджете (§3.4);
  3. ответ проверяется на совпадение даты: `dates == [D]`, иначе ответ считается неверным.
- Фид догрузки — фид с набором `trades`, `books: true` и новым флагом `history: true` в FEED (§3.9). Если у адаптера
  такого фида нет, воркер не работает, а экран пишет «адаптер не умеет сделки прошлых дат».

### 3.2 Какие даты и в каком порядке

- Кандидаты — даты основных EOD-прогонов (`store.DEFAULT_RUNS`) в интервале `[from, вчера]`. Это ровно те даты, чей
  PnL надо поправить. Выходные и даты без закрытия хаба туда не попадают. Дата без книг владельца
  (`owner_books(con, D)` пуст) получает отметку `no_books` и не запрашивается.
- `from` — дата начала, которую выбирает владелец (§8). По умолчанию — `backfill_from`. Если адаптер объявил
  `history_from` (самую раннюю дату, которую хранит сервис), берётся более поздняя из двух.
- Порядок — **от свежих дат к старым**, по одной дате. Первая всегда вчерашняя: её последний срез приходит, когда день
  закончился. Вчерашняя дата становится кандидатом с `HISTORY_DAY_FROM` (07:00 по местному времени рабочей машины,
  до начала торгов). Сегодняшнюю дату воркер не трогает никогда: её ведёт сегодняшний фид.
- Дата «уже покрыта» без запроса, если в базе есть набор `trades` за D с `report_ts` после конца D (например, ручная
  выгрузка). Такая дата получает отметку `fetched`.

### 3.3 Отметки даты и повторы

Файл `<home>/adapter-services/trades_history.json`, рядом с `state.json` сервисов. По дате хранится:
`{state, code, at, attempts, next_at, fingerprint, files: [{file, sha256, status}], units}`. Значений сделок в файле нет.

| Отметка | Когда | Повтор |
|---|---|---|
| `fetched` | ответ `complete`, файлы приняты, есть единицы приёма | даты в окне `REFRESH_BD` (3 рабочих дня от вчера) — раз в календарный день (поздние бронирования, отмены); старше — нет |
| `no_trades` | ответ `complete` с кодом `no_records`: у запрошенных книг за дату сделок нет | как у `fetched` |
| `no_books` | у владельца нет книг с позициями на D | при новом наборе позиций за D |
| `unmapped` | `partial`/`books_unmapped`: записи есть, но ни одна не попала в книги монитора; так же — ответ `complete` с другим кодом, после которого не принято ни одной единицы (адаптер не сказал, почему пусто; на экране «пусто, причина не указана») | при новом отпечатке адаптера (изменили сопоставление) |
| `unavailable` | `error`/`date_unavailable`: сервис не отдаёт эту дату | через 1, 3, 7 дней, затем только при новом отпечатке адаптера или по кнопке |
| `partial` | `partial`/`export_incomplete`, или часть файлов не принята | через `BACKOFF_MIN` (5, 15, 60 мин), как у фидов; после `MAX_ATTEMPTS` (3) — `unavailable` |
| (без отметки) | `blocked` (`login_required`, `config_invalid`, `source_disabled`), `skipped`, ошибка сети, процесса или базы, `calculation_busy` | дата не отмечается; вся догрузка ждёт: `blocked` — до входа или исправления (как пауза фида), остальное — с отступом `BACKOFF_MIN` |

Новая версия сделок даты в базе пересчёт запускает сама (§2.2). Отметки нужны только для того, чтобы решить, когда
спрашивать сервис снова: автоматически — свежие даты в окне `REFRESH_BD`, остальные — по кнопке «Перезапросить период».

### 3.4 Пересчёт, подпись и стоимость

- Пересчёт не меняется. Принятые сделки D меняют `private_inputs_hash` D. Дата в окне `WINDOW_DAYS` пересчитывается
  шагом eod на следующем цикле. Старше — шагом backfill (от старых к новым, в бюджете `backfill_budget_s`). Каждый
  пересчёт — новый EOD-прогон той же логикой `new_trades`, что сегодня (`cli.eod_run`).
- **Версию логики и подпись поднимать не нужно.** Хеш уже покрывает сделки. Подъём `VALUATION_VERSION` пересчитал бы
  всю историю, в том числе даты без сделок, и это против FlyingScotman/trading-desk-monitor#24.
- Что пересчитывается: дата с принятыми сделками по облигациям книг владельца. Для книг без отчёта позиций — ещё до
  7 следующих дат, у которых эти сделки входят в начало дня (`hist`, `MAX_HISTORY_DAYS`). Это делает план сам: у
  этих дат меняется хеш. Даты без сделок и со сделками не по облигациям не пересчитываются.
- Стоимость: один полный EOD-прогон на каждую такую дату (время одной даты — `seconds_per_date` в `backfill.json`).
  Пакеты хаба для дат истории уже в кэше, если их считал backfill; иначе backfill догрузит их, как обычно. Около 200
  рабочих дат с начала года — несколько часов фоновой работы. Она растягивается на циклы автопилота и не задерживает
  последний день. Запрос одной даты к сервису — один-два вызова (срез дня и поздние бронирования) на всё окружение.
  Время и объём даст проба адаптера (§3.9).
- Порядок двух очередей. Догрузка идёт от свежих дат к старым, пересчёт backfill — от старых к новым среди устаревших
  дат. Поскольку догрузка подаёт по одной дате за `HISTORY_GAP_S`, а backfill берёт все устаревшие даты в бюджете
  цикла, пересчёт идёт вслед за догрузкой. Порядок backfill не меняем: перенесённые спреды model price зависят от
  более ранних прогонов (`backfill.py`, модульная документация, шаг 3). Расхождение возможно только у бумаги, которую
  открыли сделки и которая оценивается model price. Её спред мог прийти из прогона D−1, ещё не пересчитанного со
  сделками. Это поправит следующий пересчёт D, если у D потом изменится вход.
- Что будет с уже посчитанной историей. Новый прогон становится основным для своей даты, старый остаётся в базе.
  PnL прошлых дат меняется по смыслу: вместо «конечное количество, переоценённое с D−1 на D» становится «позиция
  начала дня плюс PnL каждой сделки» (FlyingScotman/trading-desk-monitor#557). Вместе с ним меняются MTD и YTD.
  У книг без отчёта меняются ещё позиции, MV и риск. Риск, как в FlyingScotman/trading-desk-monitor#417: новый прогон
  считается на текущем коде и текущем ядре, поэтому цифры могут сдвинуться и по другим причинам. Пока очередь не
  пройдена, история смешанная.

### 3.5 Не мешать сегодняшним прогонам

- Не чаще одной даты за `HISTORY_GAP_S` (120 с) и не больше `HISTORY_PER_DAY` (300) запросов в сутки.
- Только когда в очереди сервисов нет ничего более срочного: заданий владельца, «Запустить сейчас», фидов по
  расписанию. Пока идёт запрос даты, сегодняшний фид ждёт его окончания: это один вызов, ограниченный таймаутом фида.
- После приёма пересчёт не запускается (§3.1): блокировка цикла держится только на время приёма.
- Пересчёт идёт шагами eod и backfill в их бюджете, последним в цикле: последний день не ждёт.
- Сегодняшняя дата не запрашивается, состояние сегодняшнего фида не трогается.
- Окно времени для догрузки (например, только вне торговых часов) — на выбор владельца (§8). По умолчанию — без окна.

### 3.6 Интерфейс (без командной строки)

- API (маршруты рядом с `api/adapter_services_routes.py`, те же `guard`, форма, `NO_STORE`):
  - `GET /api/v1/adapter-services/history` → `{available, feed, enabled, from, history_from, paused, waiting
    (login_required | config_invalid | source_disabled | null), counts {fetched, no_trades, no_books, unmapped,
    unavailable, partial, todo}, applied {in_pnl, waiting_recompute, no_effect}, current, last {date, state, at},
    next_at, problems [{date, state, code, attempts, next_at}]}`. `applied.in_pnl` — даты с принятыми сделками, у
    основного прогона которых `lineage.intraday_trades.set_ids` содержат все текущие наборы `trades` своей даты (один
    агрегатный запрос по прогонам и один по наборам, без чтения строк). Для остальных таких дат хеш
    `trades.intraday_inputs` сравнивается с хешем основного прогона, с запоминанием из пакета E. Хеш другой —
    `waiting_recompute`. Хеш тот же — `no_effect`: сделки на PnL не влияют (только не облигации или все пропущены),
    прогон не пересчитывался, и lineage о них не знает.
  - `POST /api/v1/adapter-services/history` с `enabled` и `from`: включить или выключить, дата начала.
  - `POST /api/v1/adapter-services/history/refetch` с `from` и `to`: снять отметки дат периода, кроме `no_books`, и
    поставить их в начало очереди. Ответ — число дат.
- Экран (`prototypes/settings.html`, блок «Подключение к сервисам», под фидом сделок):
  - «Сделки прошлых дат: получено N из M дат · без сделок K · не сопоставлено U · недоступно L»;
  - сейчас — «ДД.ММ», дальше — «в ЧЧ:ММ»;
  - переключатель «Догружать прошлые даты с [дата]»;
  - кнопка «Перезапросить период…» с выбором дат и подтверждением с числом дат;
  - «нужен вход», как у фидов.
  - «Диагностика»: даты «недоступно» и «не сопоставлено» с кодом и следующей попыткой.
  - «История прогонов»: строка «PnL сделок учтён в X датах, ждут пересчёта Y».
  - Тексты — в `prototypes/desk-backfill-text.js` или рядом с ним, по образцу `T.stall`.
- Экран «Сделки дня» не меняется: полоса дат (`trade_dates`) и PnL сделок (`_trade_pnl` по последнему прогону даты)
  покажут прошлые даты сами.

### 3.7 Настройки

Отдельных полей в `Settings` нет. Включение, дата начала и пауза хранятся в состоянии сервисов, как переключатель
фида (`Service.set_enabled`). Пока владелец не включит догрузку (§8), она выключена.

### 3.8 Что нужно от адаптера (договор 08 §2.2, ревизия 11; без новой минорной версии частного договора)

1. FEED: необязательные `history: true` (фид отвечает за прошлые даты с `date`) и `history_from: "YYYY-MM-DD"`
   (самая ранняя дата, которую хранит источник, если она известна). Старый монитор неизвестные ключи FEED
   отбрасывает (`clean_feeds`, `adapter_services.py:239`).
2. Закрытые коды ответа за прошлую дату:
   - `complete`/`exported` — выгрузка со сделками книг;
   - `complete`/`no_records` — у запрошенных книг за дату записей нет, а сопоставление книг работает (записей нет
     совсем, или есть только записи других книг монитора). Файл можно записать: без единиц приёма он ничего не заменит;
   - `partial`/`books_unmapped` — записи есть, но ни одна не попала в запрошенные книги. Это не «сделок нет»;
   - `error`/`date_unavailable` — источник не отдаёт эту дату;
   - остальные коды — как сейчас.
3. Проба по кнопке в панели помощника: «Проверить сделки прошлых дат». Несколько дат назад (неделя, месяц, квартал,
   начало года), для каждой — отвечает ли источник, число записей, время. Без значений. По итогу владелец или
   адаптер заполняет `history_from`.

Подробности источника — в приватном адаптере (`tasks/A12_trades_history.md`).

## 4. Крайние случаи

| Случай | Что будет |
|---|---|
| Выходной или праздник | не кандидат: у него нет основного прогона. Сделки с датой сделки в такой день не попадают ни в одну дату (`effect`: `other_trade_date`). Это известное ограничение |
| Дата без позиций или без книг владельца | `no_books`, запроса нет |
| Сделок не было | `no_trades`. Хеш прежний, пересчёта нет |
| Сделки только не по облигациям | `fetched`, хеш прежний (`trades.py:343`), пересчёта нет. В сводке — «не влияет на PnL» (`no_effect`) |
| Куплено и продано в тот же день | `_fold` суммирует сделки по строке, итоговое количество не меняется, PnL обеих сделок — в `new_trades` строки. У книги с отчётом бумага без позиции в отчёте получает нулевую строку `…\|closed`, которая хранит PnL (`trades.py:396–402`) |
| Позднее бронирование (бронировано после D с датой сделки D) | придёт в выгрузке D, сделанной позже (окно `REFRESH_BD` или «Перезапросить»). В отчёте D его может не быть: тогда `x.trades_report_gap` и предупреждение, позиции по отчёту не меняются |
| Сделку D отменили или исправили позже | новая версия или статус `cancelled` в повторной выгрузке. Новая ревизия, хеш другой, дата пересчитывается |
| Повторная выгрузка без изменений | ревизии нет (`unit_hash`), хеш прежний, пересчёта нет |
| Источник недоступен для даты | `unavailable`, воркер идёт к следующей дате |
| Сеть или вход упали | дата не отмечается, вся догрузка ждёт (§3.3) |
| Книги сервиса не сопоставлены с книгами монитора | `unmapped`, повтор после изменения сопоставления (новый отпечаток адаптера) |
| Сделки D старше 7 дней от последнего отчёта книги | как сегодня: не входят, `history_cut` в lineage |
| Отчёт позиций за D пришёл после догрузки | хеш меняется из-за `start_hash` и набора, дата пересчитывается обычным путём |
| Дата была проблемной у backfill | новый хеш, новый `Day.sig`, дата пробуется снова (`backfill.py:259–262`) |
| Сегодняшний прогон | догрузка сегодня не спрашивает. Сделки вчерашнего дня по книгам без отчёта меняют начало сегодняшнего дня, и шаг intraday пересчитает сегодняшний прогон по хешу (`autopilot.py:1192`) |
| Заморозка | старые прогоны не меняются. Новые прогоны становятся основными (`DEFAULT_RUNS`: последний complete EOD) |
| Расчёт занят (блокировка цикла) | `_ingest` ждёт до `LOCK_WAIT_S`, иначе `calculation_busy`: дата не отмечается, файлы ждут как `pending` у догрузки |
| Адаптер обновили | новый отпечаток: повтор `unmapped` и `unavailable` |
| Пакет хаба даты не в кэше | пересчитает backfill после догрузки пакета, как сейчас |

## 5. Нагрузка плана backfill

`backfill.plan` уже вызывает `trades.intraday_inputs` на каждую дату интервала (`backfill.py:251`). `backfill.status`
(экран «История прогонов» и индикатор в шапке) вызывает план при каждом опросе. Сейчас сделки есть у немногих дат, и
`apply_intraday` выходит рано. Когда сделки появятся у сотен дат, каждая дата будет читать сделки даты, набор начала
дня и сворачивать их. Решение: запоминать хеш `intraday_inputs` по дешёвому ключу. Ключ — наборы позиций даты, наборы
`trades` даты и окна `MAX_HISTORY_DAYS`, набор начала дня и настройка `intraday_trades`. Хранить в памяти процесса
(LRU). Готово, когда план на 200 синтетических датах со сделками строится за время, сравнимое с планом без сделок
(тест-замер).

## 6. Тест-план (синтетика)

`backend/tests/test_trades_history.py` (новый) и дополнения к `test_adapter_services.py`, `test_r23_backfill.py`:

1. Кандидаты: основные прогоны в `[from, вчера]`, от свежих к старым. Сегодня исключено. Вчера — только после
   `HISTORY_DAY_FROM`. `history_from` адаптера сужает интервал. Дата с набором `trades` после конца D — `fetched`
   без запроса.
2. Дата со сделками: фальшивый помощник отдаёт файл сделок D. Приём идёт без `recompute.after_inputs`. Отметка
   `fetched`. `backfill.plan` даёт D `todo` с причиной «private inputs changed». После `backfill.run` у основного
   прогона D есть `new_trades` и `lineage.intraday_trades.set_ids`, сводка — «учтено».
3. Без сделок: `complete`/`no_records`, отметка `no_trades`. Хеш и план не меняются. Повторного запроса нет вне окна
   `REFRESH_BD`.
4. `books_unmapped` → `unmapped`. Повтор только после смены отпечатка.
5. Недоступный источник: `error`/`date_unavailable` → `unavailable` с `next_at`, воркер берёт следующую дату. Ошибка
   сети: дата не отмечена, отступ всей догрузки. `login_required`: догрузка ждёт, отметок нет, сегодняшний фид и его
   `runs` не тронуты.
6. Повтор после новой версии: вторая выгрузка D с отменённой сделкой и новой версией другой даёт новую ревизию и
   другой хеш, D снова `todo`. Выгрузка с тем же содержимым ревизии не даёт, D `done`.
7. Окно `REFRESH_BD`: вчерашняя и позавчерашняя даты запрашиваются раз в календарный день, старые — нет.
   «Перезапросить период» снимает отметки и ставит даты в начало очереди.
8. Очередь сервисов: если фид по расписанию готов к запуску, догрузка ждёт. `HISTORY_GAP_S` и `HISTORY_PER_DAY`
   соблюдаются. Дата в запросе равна дате в ответе.
9. Книга без отчёта: сделки D меняют хеш D и следующих дат до 7 дней, и план даёт их `todo`.
10. Куплено и продано в тот же день в прошлой дате: PnL сделок в `new_trades`, количество строки прежнее (по образцу
    `test_pnl_new_trades.py`).
11. API: `GET` сводки на пустой базе и с датами, `POST` включения, начала и `refetch` (проверка дат,
    `invalid_request`). Без значений сделок в ответах.
12. Замер плана (§5): 200 дат со сделками.

## 8. Вопросы владельцу

1. **С какой даты пересчитывать историю.** Монитор может догрузить сделки за прошлые дни и пересчитать PnL этих дней
   так же, как сегодняшний: позиция начала дня плюс PnL каждой сделки. Цифры PnL прошлых дней, MTD и YTD изменятся.
   Варианты:
   - (а) с начала года: около 200 рабочих дней, несколько часов фоновой работы, вся история сопоставима;
   - (б) с начала текущего месяца или квартала: быстрее, сопоставимы только последние недели;
   - (в) только вперёд: монитор каждое утро догружает последний срез вчерашнего дня, старые даты не трогает.

   Если сервис хранит сделки не с начала года, раньше его даты всё равно не получится.
2. **Когда можно спрашивать сервис сделок о прошлых днях.** По одной дате раз в две минуты, не больше 300 в сутки.
   Варианты: (а) в любое время — быстрее, небольшая добавочная нагрузка на сервис днём; (б) только вне торговых часов
   (например, 20:00–08:00) — медленнее, днём сервис занят только сегодняшним фидом.

## 9. Открытые вопросы реализации

- Каким статусом приёма заканчивается файл без единиц приёма (`no_records`). Отметка `no_trades` ставится по коду
  ответа, а не по статусу файла; статус проверить тестом в пакете C, чтобы такой файл не считался «не принятым».
- Нужно ли учитывать сделки с датой сделки в нерабочий день. Сейчас они нигде не учитываются. Если да — отдельная
  задача в `stream:calc`.
