## 1. Коротко

Пересчёт уже есть. Любой прогон даты D применяет сделки D, если они лежат в базе, а подпись входов прогона их учитывает.
Как только в базе появляются сделки прошлой даты, эта дата сама становится «устаревшей»: свежие даты пересчитывает шаг
eod автопилота, старые — шаг backfill. Чего нет — **сделок прошлых дат в базе**: фид «сделки дня» по расписанию
спрашивает только сегодняшний день. Поэтому новый воркер только догружает сделки. Он идёт от свежих дат к старым, по
одной дате, через тот же фид адаптера с параметром `date`, и ведёт отметки по датам. Пересчитывают существующие шаги
автопилота. Подъём `VALUATION_VERSION` не нужен. Пересчитываются только даты, где сделки по облигациям действительно
изменили входы.

## 2. Что есть сейчас

### 2.1 Сделки в прогоне и компонента `new_trades`

- Прогон любой даты D (`cli.eod_run`, `backend/src/desk/cli.py:209`) берёт позиции `store.positions_for` и проводит
  их через `trades.intraday_inputs` (`cli.py:299`; `backend/src/desk/trades.py:450`). Внутри `apply_intraday`
  (`trades.py:272`) сделки D берутся из базы (`store.dataset_rows(con, "trades", on)`, набор `trades`, поток: дата
  берётся только своя, не переносится).
- Книга с отчётом позиций за D: позиции строго по отчёту. Позиция начала дня — предыдущий набор
  (`positions_for(on - 1)`). Сделки D дают только PnL. Расхождение отчёта и «начало дня + сделки» отмечается
  `x.trades_report_gap`. Книга без отчёта за D: её набор плюс сделки дней после отчёта (не старше
  `MAX_HISTORY_DAYS = 7`, `trades.py:110`) плюс сделки D.
- PnL изменённой позиции — PnL позиции начала дня (полная раскладка flash) плюс `new_trades`
  (`backend/src/desk/pnl/new_trades.py`, вызов `cli.py:355`). Компонента попадает в `pnl` строки прогона
  (`pnl/flash.py:353`, `pnl/direct.py:97`, `publish/desk_run.py:57` `PNL_KEYS`) и в группу «trading» сводки
  (`publish/summary.py:65`). История PnL и «PnL за период» (`api/pnl_period.py:46`) суммируют компоненты основных
  прогонов дат. Поэтому пересчитанная дата появляется там сама.
- Подпись входов: `private_inputs_hash` заменяется хешем от `[хеш позиций, применённые сделки, сделки прошлых дней,
  хеш набора начала дня, history_cut]` (`trades.py:445`). Если у даты нет сделок, сделки не по облигациям или все
  пропущены, вход возвращается без изменений (`trades.py:334`, `:343`): хеш прежний, дата не пересчитывается.
- PnL даты D не читает прогон D−1. Позиции D переоцениваются на рынке D−1 (`cli.py:345–355`). От прошлых прогонов
  зависят только перенесённые спреды model price (`store.carried_spreads`, `store/__init__.py:634`).

### 2.2 Заморозка и как дата становится устаревшей

- Прогон после `complete`/`failed` не меняется: триггеры `run_frozen` и `run_log_frozen`
  (`store/migrations/0001_init.sql:137–152`). Пересчёт — всегда **новый** прогон. Основной прогон даты — последний
  complete EOD (`store.DEFAULT_RUNS`, `store/__init__.py:567`). Старый прогон остаётся в базе.
- `backfill.plan` (`backend/src/desk/backfill.py:221`) для каждой даты с позициями и закрытием хаба сравнивает
  основной прогон с текущими входами. Хеш берётся из `trades.intraday_inputs` (`backfill.py:251`). Если он другой,
  дата получает статус `todo` с причиной «private inputs changed» (`:256`). Подпись даты `Day.sig` (`:259`) включает
  хеш, поэтому дата, проблемная на старых входах (`failed`, `MAX_ATTEMPTS = 2`, `:99`), с новыми сделками пробуется
  снова. `backfill.run` (`:405`) идёт от старых дат к новым (из-за перенесённых спредов), по одной, в пределах
  `backfill_budget_s` за цикл (600 с, `settings.py:319`), после всех остальных шагов автопилота
  (`autopilot.py:476`).
- Шаг eod автопилота (окно `WINDOW_DAYS = 14`, не больше `MAX_EOD_DATES = 10` дат, `autopilot.py:152–153`) по тому же
  признаку пересчитывает свежие даты (`autopilot.py:1049–1053`). Сегодняшние INTRADAY- и утренние прогоны — тоже по
  хешу (`autopilot.py:1192`, `:1293`).
- `recompute.after_inputs` (`backend/src/desk/recompute.py`) после приёма файлов фида сразу пересчитывает EOD даты,
  если её закрытие лежит в кэше (`recompute.py:46–75`), и сегодняшние прогоны.

### 2.3 Откуда берутся сделки

- Сделки приходят только файлами набора `trades` через обычный путь приёма. Фид «сделки дня» помощника сервисов
  адаптера (FEED с `books: true`, FlyingScotman/trading-desk-monitor#557) по расписанию вызывается без даты, то есть
  за сегодня.
- Протокол уже позволяет передать дату. `Service.run_feed(feed_id, day)` (`adapter_services.py:691`), маршрут
  `POST /api/v1/adapter-services/feeds/{id}/run` с полем `date` (`api/adapter_services_routes.py:83`), запрос
  `feed` с `date` (`adapter_services.py:1007`). Книги владельца на дату — `owner_books(con, D)`
  (`adapter_services.py:265`). Файлы идут через `scan.ingest_feed` без окна давности (`inbox/scan.py:997`, без
  `lookback`), затем `recompute.after_inputs` (`adapter_services.py:1176`).
- Повторная выгрузка той же даты с тем же содержимым новой ревизии не даёт (`unit_hash`, `inbox/scan.py:25`), и
  хеш не меняется. Изменённая выгрузка (поздние бронирования, отмены, новые версии сделок) даёт новую ревизию
  (`full_snapshot` по книге, порядок по `report_ts`, 08 §10 `trades`), и даты пересчитываются.
- Чего не хватает:
  1. никто не спрашивает фид за прошлые даты;
  2. ручной запуск с датой пишет состояние в запись самого фида (`_record(... date=day)`, `adapter_services.py:962`).
     Если такой запуск завершился ошибкой, повтор по расписанию возьмёт эту прошлую дату вместо сегодняшней
     (`adapter_services.py:931`), а пауза «нужен вход» остановит и сегодняшний фид;
  3. по ответу фида монитор не отличает «за дату сделок не было» от «книги сервиса не сопоставлены с книгами монитора»:
     в обоих случаях файл без единиц приёма;
  4. монитор не знает, какой фид умеет отвечать за прошлые даты.
- Последний срез дня. Фид идёт по расписанию в окне «с … до …», поэтому сделки D в базе — срез последнего запуска
  в день D, без вечерних сделок и поздних бронирований. Выгрузка D, сделанная после конца D, даёт срез на конец дня.

## 3. Проект

### 3.1 Где живёт воркер

Отдельного потока и нового фреймворка нет. Воркер — ещё одна ветка в рабочем цикле `adapter_services.Service`.
Помощник адаптера и так вызывается по одному процессу за раз, под `HELPER_LOCK`, а приём файлов фида берёт блокировку
цикла автопилота (`CycleLock`, не реентерабельная). Вызывать помощника из шага автопилота нельзя: главный довод не в
блокировке (приём внутри цикла ждал бы сам себя до `LOCK_WAIT_S` и кончился бы `calculation_busy`), а в том, что сетевой
вызов к сервису внутри цикла держал бы расчёт сегодняшних прогонов на всё время запроса.

- Модуль `backend/src/desk/trades_history.py` без потоков и без вызовов помощника. В нём: кандидаты, порядок, отметки,
  файл состояния, сводка для экрана.
- `Service._step`: после заданий владельца, «Запустить сейчас» и фидов по расписанию (`_scheduled()` не нашёл готового
  фида) вызывается `_history_step()`.
- `_history_fetch` использует то же, что `_feed`: книги владельца на D (`owner_books(con, D)`), обрезку запроса по
  пределам (`_fit_books`, общая с `_feed`), `_call(..., "feed", {"feed", "date", "book"})`, проверку ответа
  `clean_feed_result`, приём `_ingest`. Отличия от `_feed`:
  1. состояние пишется в `trades_history.json`, а не в `runs[<фид>]`: расписание, повторы и пауза «нужен вход»
     сегодняшнего фида от догрузки не зависят;
  2. `_ingest(..., recompute_runs=False, wait=False)`: после приёма не вызывается `recompute.after_inputs`; блокировка цикла
     берётся **одной неблокирующей попыткой** (`_try_cycle_lock`). Не вышло — файлы остаются `pending` в
     `trades_history.json`, `HELPER_LOCK` отпускается сразу, а приём повторяется на следующем шаге **до** запроса новой
     даты (`_history_drain`, без `HELPER_LOCK`). Каталог `pending` не удаляет `_prune`. Сегодняшний фид и «Запустить сейчас»
     не ждут блокировку цикла вместо догрузки;
  3. ответ проверяется на совпадение даты: `dates` пуст или `== [D]`, иначе ответ неверный и отметки нет;
  4. помощник берётся без ожидания (`HELPER_LOCK.acquire(timeout=0.25)`): занят — шаг пропущен.
- Фид догрузки — фид набора `trades` с `books: true` и `history: true` (§3.8). Если у адаптера такого фида нет, воркер не
  работает, а экран пишет «Адаптер не умеет сделки прошлых дат».
- Запись `trades_history.json` — только под `Service._lock` и атомарно (`os.replace`), как `write_state`: пишут и поток
  сервиса, и маршруты API.

### 3.2 Какие даты и в каком порядке

- Кандидаты — даты основных EOD-прогонов (`store.default_runs`) в интервале `[from, вчера]`. Выходные и даты без закрытия
  хаба туда не попадают, а рабочая суббота с закрытием хаба — кандидат (фид дня по субботам не работает,
  `weekdays_only`, а этот спрашивает с датой). Дата без книг владельца (`owner_books(con, D)` пуст) получает отметку
  `no_books` и не запрашивается.
- `from` выбирает владелец. По умолчанию — начало текущего года, но не раньше начала истории (`backfill_from`).
  **Снизу `from` ограничен настройкой `backfill_from`** (раньше неё никто не пересчитает дату) и объявленной адаптером
  `history_from`. Если история прогонов выключена (`settings.backfill`), экран пишет «ждут пересчёта … (история прогонов
  выключена)».
- Порядок — **блоками по 10 кандидатов, от свежего блока к старому, внутри блока от старой даты к новой**. У книг без
  отчёта сделки даты D входят в начало дней D+1…D+7 (`hist`); если идти от свежих к старым по одной дате, каждая новая
  догрузка снова сделала бы устаревшими уже пересчитанные более новые даты (до 8 пересчётов на дату). Блоки закреплены
  за списком кандидатов, а не за тем, что осталось спросить, поэтому блок заканчивается раньше следующего. Даты, которые
  владелец перезапросил кнопкой, идут первыми.
- Вчерашняя дата — кандидат с `HISTORY_DAY_FROM` (07:00 местного времени); сегодняшнюю воркер не трогает никогда.
- Дата покрыта без запроса (`fetched`, код `covered`), если в базе есть набор `trades` за D, у которого дата `report_ts`
  по Москве **позже D** (ручная выгрузка после конца дня). Конца дня адаптера (`eod_time`) монитор не знает, поэтому
  срез последнего запуска в тот же день покрытием не считается.

### 3.3 Отметки даты и повторы

Файл `<home>/adapter-services/trades_history.json`, рядом с `state.json`. По дате хранится
`{state, code, at, attempts, next_at, fingerprint, files: [{file, sha256, status}], units}`, значений сделок нет.

| Отметка | Когда | Повтор |
|---|---|---|
| `fetched` | ответ `complete`, файлы приняты, есть единицы приёма (или файл — копия уже принятого) | даты в окне `REFRESH_BD` (3 новейших кандидата) — раз в календарный день; старше — нет |
| `no_trades` | `complete`/`no_records` (оба случая §3.8): отметка по коду, не по статусу файла | как у `fetched` |
| `no_books` | у владельца нет книг с позициями на D | при новом наборе позиций за D |
| `unmapped` | `partial`/`books_unmapped`; а также `complete` с другим кодом, после которого нет ни файлов, ни принятых единиц (на экране «пусто, причина не указана») | при новом отпечатке адаптера |
| `unavailable` | `error`/`date_unavailable` (или `partial` `MAX_ATTEMPTS` раз) | через 1, 3, 7 дней, затем только при новом отпечатке или по кнопке |
| `partial` | `partial`/`export_incomplete`, или часть файлов не принята | через 5, 15 мин; на третий раз — `unavailable` |
| (без отметки) | `blocked` (`login_required`, `config_invalid`, `source_disabled`): вся догрузка ждёт входа или исправления; `skipped`, ошибка сети, процесса или базы: отступ всей догрузки `BACKOFF_MIN` (5, 15, 60 мин); блокировка цикла занята: файлы `pending` | дата не отмечается |

Если все прошлые даты (не меньше трёх) «недоступны», экран подсказывает проверить настройки подключения.
Новая версия сделок даты в базе пересчёт запускает сама (§2.2). Отметки нужны только для того, чтобы решить, когда
спрашивать сервис снова.

### 3.4 Пересчёт, подпись и стоимость

- Пересчёт не меняется. Принятые сделки D меняют `private_inputs_hash` D; дату пересчитывают шаги автопилота (§3.5).
  Каждый пересчёт — новый EOD-прогон той же логикой `new_trades` (`cli.eod_run`). **Версию логики и подпись поднимать не
  нужно**: хеш уже покрывает сделки, а подъём `VALUATION_VERSION` пересчитал бы всю историю (против
  FlyingScotman/trading-desk-monitor#24).
- Пересчитывается дата с принятыми сделками по облигациям книг владельца. Для книг без отчёта — ещё до 7 следующих дат
  (`hist`). Даты без сделок и со сделками не по облигациям не пересчитываются (`no_effect`).
- Стоимость: один полный EOD-прогон на дату (время одной даты — `seconds_per_date` в `backfill.json`), с блоками по 10 дат
  повторных пересчётов почти нет. Около 200 рабочих дат с начала года — несколько часов фоновой работы.
- Порядок двух очередей. Догрузка идёт блоками от свежих дат к старым, пересчёт backfill — от старых к новым среди
  устаревших дат (перенесённые спреды model price зависят от более ранних прогонов, порядок backfill не меняем). Расхождение
  возможно только у бумаги, которую открыли сделки и которая оценивается model price; его поправит следующий пересчёт.
- **Полнота PnL сделок.** Дата, у которой в lineage есть `set_ids` нужных наборов `trades`, ещё не значит, что PnL всех
  сделок вошёл в итог (нет предыдущего закрытия; позиция начала дня без PnL; бумага не оценена; сделка без цены или
  курса). Эти случаи ведёт lineage прогона: ключи `intraday_trades.no_pnl`, `.lost`, `.unpriced`, `.no_prev_close`
  (число и сумма; их пишут расчётные пакеты stream:calc, а не этот проект). Экран и API читают их и показывают «учтён
  полностью / частично / вне PnL (причина)»; если ключей нет — «нет данных о полноте». Первая дата интервала (нет
  предыдущего закрытия) PnL сделок не получит. Потеря PnL «купил и продал новую бумагу в тот же день» чинится отдельно
  (stream:calc).
- Что будет с уже посчитанной историей. Новый прогон становится основным для своей даты, старый остаётся в базе. PnL
  прошлых дат меняется по смыслу (FlyingScotman/trading-desk-monitor#557), вместе с ним MTD и YTD; у книг без отчёта
  меняются позиции, MV и риск. Новый прогон считается на текущем коде и ядре, поэтому цифры могут сдвинуться и по другим
  причинам. Пока очередь не пройдена, история смешанная.

### 3.5 Не мешать сегодняшним прогонам

- Не чаще одной даты за `HISTORY_GAP_S` (120 с) и не больше `HISTORY_PER_DAY` (300) запросов в сутки (счётчик пишется
  до вызова: перезапуск его не обнуляет). Не начинать запрос, если фид по расписанию наступит раньше, чем закончился бы
  прошлый запрос догрузки (`next_due`, не меньше 30 с): иначе он ждал бы весь вызов.
- Только когда нет ничего более срочного: заданий владельца, «Запустить сейчас», фидов по расписанию. Помощник занят —
  шаг пропущен.
- Окно времени: «только вне торговых часов» (по умолчанию; будни 09:30–19:45 по Москве, `autopilot.in_trading_hours`) или
  «в любое время» — выбирает владелец.
- **Шаг eod автопилота** идёт до intraday и бюджета не имеет. Поэтому в торговые часы он не пересчитывает прошлые даты (кроме
  последней даты с позициями и дат, которые запросил сам цикл), у которых единственная причина — «private inputs changed».
  Их берёт шаг backfill (после intraday, свой бюджет `backfill_budget_s`): они не помечаются как уже пробованные. Вне торговых
  часов шаг eod считает их, как раньше. При выключенной истории прогонов (`settings.backfill`) шаг eod считает их всегда.
  Тест: «пересчёт вчерашней даты не задерживает шаг intraday того же цикла».
- Сегодняшняя дата не запрашивается, состояние сегодняшнего фида не трогается.

### 3.6 Интерфейс (без командной строки)

- API (`api/adapter_services_routes.py`, те же `guard`, форма, `NO_STORE`):
  - `GET /api/v1/adapter-services/history` → `{available, code, feed, enabled, when, from, from_min, from_default,
    history_from, backfill_enabled, paused, waiting (login_required | config_invalid | source_disabled | not_ready |
    null), gate (off | trading_hours | daily_limit | gap | backoff | null), counts {fetched, no_trades, no_books, unmapped,
    unavailable, partial, todo, covered}, dates, applied {full, partial, outside, unknown, waiting_recompute, no_effect,
    in_pnl, reasons}, current, last, next_at, hint, problems [{date, state, code, attempts, next_at}], calls_today,
    limit_per_day}`. `applied` читается по основному прогону каждой даты: `lineage.intraday_trades.set_ids` содержат
    новейший набор `trades` даты → полнота по ключам §3.4; иначе хеш `trades.intraday_inputs` (с запоминанием, §5) сравнивается
    с хешем прогона: другой — `waiting_recompute`, тот же — `no_effect`.
  - `POST /api/v1/adapter-services/history` с любым из `enabled` (`true`/`false`), `from` (дата, ограничена снизу
    `backfill_from`), `when` (`off_hours`/`any`).
  - `POST /api/v1/adapter-services/history/refetch` с `from`, `to` и необязательным `confirm=true`. Без `confirm` ответ
    `{state: "confirm", dates: N}` и ничего не меняется; с `confirm` — отметки дат периода (кроме `no_books`) сняты, даты
    поставлены первыми, ответ — число дат.
- Экран (`prototypes/settings.html` блок «Подключение к сервисам» под таблицей фидов, код `prototypes/desk-services.js`,
  слова `prototypes/desk-backfill-text.js`, `T.history`):
  - переключатель «Догружать сделки прошлых дат с [дата]» (по умолчанию выключен);
  - список «Когда спрашивать сервис»: «Только вне торговых часов (по умолчанию)» / «В любое время»;
  - кнопка «Перезапросить период…»: выбор дат и подтверждение с числом дат;
  - сводка «Сделки прошлых дат: получено N из M дат · без сделок K · не сопоставлено U · недоступно L · ждут запроса T»;
  - строка «PnL сделок учтён полностью в …, частично в …, вне PnL в … (причины). Ждут пересчёта: Y. Не влияют на PnL: Z»;
  - «Сейчас: ДД.ММ», либо причина ожидания («нужен вход», «ждёт конца торговых часов, дальше в ЧЧ:ММ»);
  - «Диагностика»: даты «недоступно», «не сопоставлено», «получено частично» с кодом и следующей попыткой;
  - «Адаптер не умеет сделки прошлых дат.» — если фид не объявляет `history`;
  - «История прогонов»: строка «Сделки прошлых дат: PnL сделок учтён в X датах, ждут пересчёта Y».
- Экран «Сделки дня» не меняется: полоса дат и PnL сделок покажут прошлые даты сами.
- Тесты экрана — `tests/js/services.pw.test.js`.

Отдельных полей в `Settings` нет. Включение, дата начала, часы и отметки хранятся в `trades_history.json`. Пока владелец не
включит догрузку (§8), она выключена.

### 3.8 Что нужно от адаптера (договор 08 §2.2, ревизия 11; без новой минорной версии частного договора)

1. FEED: необязательные `history: true` (фид отвечает за прошлые даты с `date`) и `history_from: "YYYY-MM-DD"`. Старый
   монитор неизвестные ключи FEED отбрасывает (`clean_feeds`).
2. Закрытые коды ответа за прошлую дату (итоговая семантика адаптера, FlyingScotman/trades-data-adapter#145):
   - `complete`/`exported` — в файлах записи запрошенных книг;
   - `complete`/`no_records` — два случая. (а) Записей в снимке нет вовсе: файл **без единиц приёма**, он ничего не заменяет и
     дату не меняет. (б) Записи есть, сопоставление книг доказано, но запрошенных книг среди них нет: файл с **пустыми
     единицами** всех запрошенных книг, он заменяет их пустым списком (удалённая в источнике сделка уходит из даты). В обоих
     случаях монитор ставит `no_trades` по коду;
   - `partial`/`books_unmapped` — записи есть, но ни одна не доказала сопоставление: единиц нет, книги не заменяются. Это
     не «сделок нет»; повтор после нового отпечатка;
   - `error`/`date_unavailable` — только прошлая дата: отказ сервиса на окно даты (4xx, кроме 401, 403, 408, 429), файла нет;
     для сегодняшней даты 4xx остаётся `partial`/`export_incomplete`. Если так на всех датах — вероятно, настройки;
   - остальные коды — как у фидов.
   Принятый риск адаптера: единственная сделка всего окружения, удалённая в источнике, остаётся в дате, пока не появится другая
   запись. Источники `possvc_trades` и `trades_hourly` на одни книги не включать (единица даты принадлежит одному источнику).
3. Проба по кнопке в панели помощника: «Проверить сделки прошлых дат» (несколько дат назад, без значений). По итогу владелец
   или адаптер заполняет `history_from`.

Подробности источника — в приватном адаптере (`tasks/A12_trades_history.md`).

## 4. Крайние случаи

| Случай | Что будет |
|---|---|
| Выходной или праздник | не кандидат: у него нет основного прогона. Сделки с датой сделки в такой день не попадают ни в одну дату (`effect`: `other_trade_date`). Это известное ограничение |
| Дата без позиций или без книг владельца | `no_books`, запроса нет |
| Сделок не было | `no_trades`. Хеш прежний, пересчёта нет |
| Сделки только не по облигациям | `fetched`, хеш прежний (`trades.py:343`), пересчёта нет. В сводке — «не влияют на PnL» (`no_effect`) |
| Куплено и продано в тот же день | у **удерживаемой** позиции `_fold` суммирует сделки по строке, количество не меняется, PnL обеих сделок — в `new_trades`. У **новой** бумаги (не было на начало дня) нулевая строка сейчас пропадает вместе с PnL сделок; это чинится отдельно (stream:calc), пока PnL таких сделок в датах истории не учтён |
| Позднее бронирование (бронировано после D с датой сделки D) | придёт в выгрузке D, сделанной позже (окно `REFRESH_BD` или «Перезапросить»). В отчёте D его может не быть: тогда `x.trades_report_gap` и предупреждение, позиции по отчёту не меняются |
| Сделку D отменили или исправили позже | новая версия или статус `cancelled` в повторной выгрузке. Новая ревизия, хеш другой, дата пересчитывается |
| Повторная выгрузка без изменений | ревизии нет (`unit_hash`), хеш прежний, пересчёта нет |
| Источник недоступен для даты | `unavailable`, воркер идёт к следующей дате |
| Сеть или вход упали | дата не отмечается, вся догрузка ждёт (§3.3) |
| Книги сервиса не сопоставлены с книгами монитора | `unmapped`, повтор после изменения сопоставления (новый отпечаток адаптера) |
| Сделки D старше 7 дней от последнего отчёта книги | как сегодня: не входят, `history_cut` в lineage |
| Отчёт позиций за D пришёл после догрузки | хеш меняется из-за `start_hash` и набора, дата пересчитывается обычным путём |
| Дата была проблемной у backfill | новый хеш, новый `Day.sig`, дата пробуется снова (`backfill.py:259–262`) |
| Сегодняшний прогон | догрузка сегодня не спрашивает. Сделки вчерашнего дня по книгам без отчёта меняют начало сегодняшнего дня, и шаг intraday пересчитает сегодняшний прогон по хешу (`autopilot.py:1192`) |
| Заморозка | старые прогоны не меняются. Новые прогоны становятся основными (`DEFAULT_RUNS`: последний complete EOD) |
| Расчёт занят (блокировка цикла) | одна неблокирующая попытка; не вышло — файлы `pending` в `trades_history.json`, помощник свободен, приём на следующем шаге до нового запроса |
| Адаптер обновили | новый отпечаток: повтор `unmapped` и `unavailable` |
| Пакет хаба даты не в кэше | пересчитает backfill после догрузки пакета, как сейчас |

## 5. Нагрузка плана backfill

`backfill.plan` вызывает `trades.intraday_inputs` на каждую дату интервала, а `backfill.status` (экран «История прогонов» и
индикатор в шапке) вызывает план при каждом опросе. Когда сделки появятся у сотен дат, каждая дата читала бы сделки даты,
набор начала дня и сворачивала их. Решение (пакет E, только `backfill.py`, `trades.py` не меняется):
`backfill.inputs_hash(con, d, settings, stamp)` запоминает хеш в памяти процесса (LRU на 4096 записей) под ключом
`backfill.inputs_stamp`: база, число и новейший id **всех** наборов позиций и **всех** наборов данных (в них сделки даты и
60 предыдущих дней для `history_cut`, набор начала дня, условия сделок) и настройка `intraday_trades`. Наборы не меняются,
новая ревизия — новая строка, поэтому любое изменение входов любой даты меняет ключ: устаревшего хеша не бывает. Цена —
два агрегатных запроса на план. Тест замера: план на 200 датах со сделками второй раз не вызывает `intraday_inputs` вовсе и не
медленнее плана без сделок; новая ревизия сделок одной даты меняет ключ, а все хеши равны хешам без запоминания. Шаг eod
автопилота хеши не запоминает (до 10 дат).

   если все даты недоступны — подсказка в сводке.

9. `no_books` и повтор при новых позициях.
10. Файлы `pending` при занятой блокировке цикла: помощник свободен, сегодняшний фид не ждёт, `_prune` их не трогает, приём на

11. Шаг eod автопилота в торговые часы оставляет даты с «private inputs changed» backfill; вне часов и при выключенном backfill
    считает; дата, о которой попросил цикл, считается всегда.
12. API: `GET` сводки, `POST` включения/даты/часов, `refetch` (проверка дат, `invalid_request`), без значений сделок.
13. Замер плана (§5): 200 дат со сделками.
14. Экран: переключатель с датой, список часов, «Перезапросить период…» с подтверждением числа дат, сводка и полнота,
    «нужен вход», «выключена история прогонов», «Адаптер не умеет сделки прошлых дат», строка «История прогонов».

Не покрыто здесь: потеря PnL «купил и продал новую бумагу» и сами ключи полноты lineage (stream:calc); повторные пересчёты
книг без отчёта в блоке измеряются только порядком обработки.

## 8. Вопросы владельцу

Решения ещё не получены, поэтому догрузка по умолчанию выключена, а оба параметра выбираются на экране.

1. **С какой даты пересчитывать историю.** Монитор может догрузить сделки за прошлые дни и пересчитать PnL этих дней так же,
   как сегодняшний: позиция на начало дня плюс PnL каждой сделки. Цифры PnL прошлых дней, MTD и YTD изменятся; первая дата
   истории PnL сделок не получит (нет предыдущего закрытия). Варианты: (а) с начала года — около 200 рабочих дней, несколько
   часов фоновой работы, вся история сопоставима (значение по умолчанию на экране); (б) с начала месяца или квартала — быстрее,
   сопоставимы только последние недели; (в) только вперёд — каждое утро последний срез вчерашнего дня. Раньше начала истории
   прогонов и раньше даты, которую хранит сервис, дату выбрать нельзя.
2. **Когда можно спрашивать сервис сделок о прошлых днях.** По одной дате раз в две минуты, не больше 300 в сутки. (а) Только вне
   торговых часов (будни 09:30–19:45 по Москве) — по умолчанию, медленнее, днём сервис занят только сегодняшним фидом;
   (б) в любое время — быстрее, небольшая добавочная нагрузка днём.

## 9. Открытые вопросы реализации

- Статус приёма файла `no_records` без единиц проверен тестом: отметка ставится по коду, статус файла не важен.
- Сделки с датой сделки в нерабочий день (без закрытия хаба) нигде не учитываются. Если нужно — отдельная задача в `stream:calc`.
- Ключи полноты lineage (`no_pnl`, `lost`, `unpriced`, `no_prev_close`, число и сумма) пишет stream:calc; пока их нет, экран пишет
  «нет данных о полноте».
