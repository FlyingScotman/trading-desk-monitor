# Trading Desk Monitor — контракт данных (версия 1.1)

Документ описывает, **что** должен посчитать расчётный сервис, **куда** он это кладёт и **как** интерфейс это забирает.
Это договор между двумя независимыми частями:

- **расчётный сервис** — ваш продукт поверх in-house либы, статики и рыночных данных. Он только пишет.
- **монитор** (этот репозиторий) — база, веб-сервер и 4 страницы UI. Он только читает.

Пока контракт соблюдён, части меняются независимо друг от друга.

> Этот документ — про **результаты расчётов** (слой 2 центрального сервиса). Входные данные (справочники, срезы, рынок)
> описаны в `docs/DATA_REQUIREMENTS.md`, общая картина — в `docs/SERVICE_DATA_MODEL.md`, сценарии — в `docs/SCENARIOS.md`.
>
> Упрощения, если входной слой загружен:
> - `run.add_reference_data()` — вместо `add_books / add_issuers / add_curves / add_fx / add_indices`: статика и рынок на `as_of` берутся из сервиса (кривые интерполируются на 11 пилларов, `move_bp` и `move_pct` — к предыдущей дате);
> - позиции и сделки ссылаются на эмитента кодом `issuer_id`, монитор показывает его имя;
> - если в `pnl.official` пусто, при публикации берётся официальный PnL из `pnl_official` (тот же `position_id`);
> - полную переоценку сценариев можно приложить к уже опубликованному прогону: `tdm.writer.attach_scenario_results(...)`.

Связанные файлы:

| Файл | Что это |
|---|---|
| `tdm/schema.sql` | DDL базы (SQLite) — первоисточник по таблицам и колонкам |
| `contract/bundle.schema.json` | JSON Schema пакета прогона (для загрузки файлом) |
| `fixtures/demo_bundle.json` | полный пример пакета: 88 позиций, 22 сделки фондирования, 8 сценариев |
| `tdm/writer.py` | Python-SDK записи (`Run`) |
| `examples/calc_service_stub.py` | шаблон расчётного сервиса, запускается как есть |

## 1. Архитектура

```
 ┌───────────────────────────┐        ┌──────────────────────┐        ┌───────────────────────────┐
 │ Расчётный сервис          │ пишет  │  SQLite  tdm.sqlite  │ читает │ Веб-сервер  python -m tdm │
 │ in-house либа + статика   ├───────►│  (режим WAL)         ├───────►│ serve  :8080              │
 │ + рыночные данные         │        │                      │        │  /desk-data.js, /api/v1/* │
 └───────────────────────────┘        └──────────────────────┘        └─────────────┬─────────────┘
   способ A: tdm.writer.Run (Python, прямые вставки)                                │ HTTP
   способ B: JSON-пакет → python -m tdm import file.json                            ▼
                                                                      браузеры пользователей
                                                                      (Desk Monitor, Widget Board,
                                                                       Pivot Studio, Scenario Lab)
```

**Почему база, а не API расчётного сервиса.**
- Расчёт может идти долго и падать. UI при этом должен показывать последний удачный срез.
- Расчётному сервису не нужно держать сервер, отвечать пользователям и думать о нагрузке.
- Прошлые прогоны остаются в базе: можно открыть любой день или интрадей-прогон и сравнить.
- SQLite — это один файл и ноль установки. Режим WAL позволяет одному писателю работать параллельно с любым числом читателей; для деска этого с запасом. Если позже понадобится PostgreSQL или MS SQL, схема переносится почти один к одному: типы простые, нет специфики SQLite, кроме `AUTOINCREMENT`.

**Где лежит файл.** По умолчанию это `data\tdm.sqlite` в папке монитора. Переопределяется переменной окружения `TDM_DB` или параметром `--db`. Расчётный сервис и веб-сервер должны указывать на **один и тот же** файл. Держите его на локальном диске машины, где крутится сервер: SQLite на сетевой шаре (SMB) работает ненадёжно.

## 2. Прогон: единица публикации

Всё, что пишет расчётный сервис, привязано к **прогону** (`calc_run`).

```
 Run(...)                      add_*(...)                     publish()
 status='loading'  ─────────►  данные пишутся порциями  ────► проверки ──ok──► status='complete'  (видно в UI)
     │                                                           │
     └──────────── исключение / ошибка проверки ────────────────┴──────────► status='failed'    (не видно)
```

| Правило | Что значит |
|---|---|
| UI видит **только** `status='complete'` | Полузаписанный или упавший прогон никто не увидит. Публикация атомарна: одна транзакция меняет статус |
| По умолчанию показывается **последний опубликованный** прогон | Сортировка: `as_of`, затем `published_at`, затем `run_id`. Интрадей за сегодня вытесняет вчерашний EOD, новый EOD — интрадей |
| Любой прогон можно открыть явно | `?run_id=123` или `?as_of=2026-10-13` в адресе страницы; есть выпадающий список внизу слева |
| Прогоны неизменяемы | Чтобы исправить данные, сделайте новый прогон. Старый остаётся в истории; `python -m tdm purge` чистит старые |
| `run_type` | `EOD` — официальный срез дня, пишет строку в историю `desk_history`. `INTRADAY` — промежуточный, в историю не пишет. `TEST` — для проверок |

Поля `calc_run`, которые заполняет расчётный сервис:

| Поле | Обяз. | Описание |
|---|---|---|
| `as_of` | да | дата среза `YYYY-MM-DD`. От неё считаются сроки (`tenor_y`) |
| `run_type` | да | `EOD` / `INTRADAY` / `TEST` |
| `source` | нет | кто считал (имя сервиса, хост) — видно в списке прогонов |
| `lib_version` | нет | версия расчётной либы — для разборов «почему цифра изменилась» |
| `market_snapshot` | нет | идентификатор набора рыночных данных (например, «закрытие МосБиржи 18:45») |
| `comment` | нет | свободный текст |

`started_at`, `published_at`, `status`, `error` и `contract_version` заполняются автоматически.

## 3. Общие конвенции

| Тема | Правило |
|---|---|
| Валюта отчётности | **RUB**. Все `*_rub` и все суммы без указания валюты — в рублях |
| Валютные суммы | `notional`, `mv`, `fx_delta`, `funding.amount` — в валюте инструмента (`ccy`) |
| Курсы | `mkt_fx.rate` — RUB за 1 единицу валюты. `RUB` = 1 (SDK добавит сам) |
| Ставки, доходности, купоны | в **процентах**: 14.5 значит 14.5 % |
| Спреды и сдвиги кривых | в **базисных пунктах** |
| DV01 / CS01 | изменение PV в **RUB** при сдвиге **+1 б.п.** Длинная облигация → DV01 < 0. Pay-fixed IRS → DV01 > 0. Покупка защиты CDS → CS01 > 0 |
| FX-дельта | позиция в единицах валюты; **+** = длинная валюта (выигрывает от ослабления рубля) |
| Фондирование | `amount < 0` — привлечение (РЕПО, FTP), `amount > 0` — размещение. Стоимость привлечения в `carry` получается отрицательной |
| PnL | + = прибыль, за один день (`as_of − 1 раб. день → as_of`), в RUB |
| Даты | ISO `YYYY-MM-DD`; метки времени — `YYYY-MM-DDTHH:MM:SS` |
| Идентификаторы | `position_id` и `deal_id` — **стабильны между днями** (номер сделки или позиции во фронт-системе). По ним UI помечает новые сделки и сопоставляет дни |

### 3.1 Фиксированные справочные ключи (UI v1)

Прототипы UI в нескольких местах ссылаются на ключи по имени. Пока UI не доработан, используйте **именно эти** значения:

| Что | Значения |
|---|---|
| Бакеты (`ref_bucket`) | `1M 3M 6M 1Y 2Y 3Y 5Y 7Y 10Y 15Y 20Y+`, пилларсы 1/12, 0.25, 0.5, 1, 2, 3, 5, 7, 10, 15, 20 лет. Каждая кривая — точка на **каждом** бакете |

| Валюты | `RUB`, `USD`, `CNY`, `EUR`. Курс любой другой валюты UI покажет, но фильтры, слайдеры Scenario Lab и Pivot Studio знают только эти четыре |

| `instr_type` | `BOND`, `IRS`, `XCCY`, `CDS`, `FX` |

| Рейтинги | шкала `ref_rating` (AAA … D); новые значения из `run_issuer` добавляются в конец |

`asset_class`, `type` фондирования и `desk` — свободный текст; UI группирует по ним как есть.

## 4. Что нужно посчитать и выложить

### 4.1 Статика на прогон

Статика пишется **в каждом прогоне** (снимок). Тогда прошлый день показывается так, как был посчитан, даже если справочник с тех пор изменился. Объём маленький.

**`run_book`** — книги (`add_books`). Порядок списка = порядок в UI.

| Поле | Обяз. | Описание |
|---|---|---|
| `book_id` | да | ключ: `OFZ`, `CORP_RUB`, … |
| `name` | да | название для экрана |
| `desk` | да | деск, к которому относится книга (фильтр «Деск») |
| `trader` | нет | ответственный |

**`run_issuer`** — эмитенты и референсы CDS (`add_issuers`). Каждый `position.issuer` должен здесь быть.

| Поле | Обяз. | Описание |
|---|---|---|
| `issuer` | да | ключ (как в `position.issuer`) |
| `issuer_group` | да | группа связанных заёмщиков — основа концентраций |
| `sector` | нет | отрасль |
| `rating` | нет | рейтинг по шкале `ref_rating` |
| `is_gov` | нет | суверен РФ: влияет на сегмент «Гос» и сценарные спред-шоки |
| `is_quasi` | нет | квазисуверен (справочно) |

### 4.2 Рыночные данные на прогон

**`run_curve` + `mkt_curve_point`** (`add_curves`): по каждой кривой 11 точек.

| Поле | Описание |
|---|---|
| `curve_id`, `name`, `ccy`, `kind` | ключ, подпись, валюта, `bond` / `swap` |
| `points[].rate` | уровень кривой на срез, % |
| `points[].move_bp` | изменение за день, б.п. — **то самое**, что использовано в PnL explain (`rates`); UI показывает его рядом с кривой и строит матрицу «DV01 × сдвиг» |

**`mkt_fx`** (`add_fx`): `ccy`, `rate` (RUB за 1 ед.), `move_pct` (изменение курса за день, %).
**`mkt_index`** (`add_indices`): `index_name`, `value` в %.

#### 4.3.1 Key-rate DV01 — `position_risk`

В пакете это поле `risk: {curve_id: {bucket: dv01}}`; нулевые бакеты можно не писать.

- Это **главная чувствительность** монитора. На ней строятся теплокарты «кривая × бакет», лестницы DV01, PnL explain по ставкам и все сценарии без полной переоценки.
- Методика: сдвиг на +1 б.п. одного пиллара кривой (треугольная функция между соседними пилларами), остальные пилларсы неподвижны; результат — ΔPV в RUB. Должно выполняться Σ по бакетам и кривым = `position.dv01`. При расхождении больше 0.1 % SDK пишет предупреждение.
- Кривые по типам:
  - фиксированные облигации → кривая своей валюты (RUB → `RUB OFZ`);
  - флоатеры на КС → `RUB KEY`, на RUONIA → `RUB RUONIA` (короткий конец);
  - IRS → кривая своего индекса;
  - XCCY → иностранная кривая + `RUB RUONIA`;
  - FX-форварды → обе кривые (дифференциал ставок).
- Позиция может иметь риск на нескольких кривых.

#### 4.3.2 FX-дельта — `position_fx`

В пакете — `fx_delta: {ccy: amount}`: позиция в единицах валюты.
- Валютная облигация: `{ccy: mv}`.
- FX-сделка: сумма со знаком.
- XCCY: ± валютный номинал.

Рублёвые инструменты — пусто. Из этих данных и фондирования собирается ОВП.

#### 4.3.3 Вторые производные — `position_gamma` (гамма, выпуклость, кросс-гамма)

В пакете — `gamma: [[factor_1, factor_2, d2PV], …]`. Это разреженная симметричная матрица вторых производных PV позиции (в RUB) по факторам. Каждая пара задаётся **один раз**, порядок факторов в паре не важен: SDK сам приводит пару к виду `factor_1 ≤ factor_2`.

| Фактор | Что сдвигается | Единица |
|---|---|---|
| `IR\|<curve_id>\|<bucket>` | один пиллар кривой (как в key-rate DV01) | 1 б.п. |
| `CS` | собственный кредитный спред позиции (тот, к которому считается CS01) | 1 б.п. |
| `FX\|<ccy>` | курс валюты к рублю | 1 % |

`d2PV` = ∂²PV_RUB / (∂a ∂b), в RUB на (единица a × единица b). Вклад в PnL сценария:

```
PnL₂ = Σ_a ½·Γ_aa·Δa²  +  Σ_{a<b} Γ_ab·Δa·Δb
```

**Что считать (методика — конечными разностями в вашей либе, теми же сдвигами, что и для DV01/CS01):**

| Блок | Формула | Кому нужен | Приоритет |
|---|---|---|---|
| ставки × ставки | `[PV(+h_i,+h_j) − PV(+h_i,−h_j) − PV(−h_i,+h_j) + PV(−h_i,−h_j)] / 4h²`; диагональ: `[PV(+h_i) + PV(−h_i) − 2PV] / h²`, h = 1 б.п. (лучше 10 б.п. с пересчётом на 1 б.п.²) | облигации, IRS, XCCY, FX-форварды | ● облигации и свопы |
| спред × спред, ставки × спред | то же по `CS` и паре `IR`×`CS` | облигации, CDS | ● облигации с CS01 ≠ 0 |
| курс × ставки, курс × спред | `∂DV01_RUB/∂FX%`: для бумаги в валюте = DV01_i(RUB)/100, CS01/100 | валютные бумаги, XCCY, CNY/USD-свопы | ○ — монитор вычислит сам, если блока нет |

**Разреженность.** При линейной интерполяции кривой поток зависит только от двух соседних пилларов, поэтому матрица «ставки × ставки» по одной кривой **трёхдиагональная**: на облигацию около 20 элементов. Пары разных кривых нужны, только если инструмент реально зависит от обеих (XCCY, FX-форвард). Нулевые элементы не передавайте.

**Минимальный вариант.** Если матрицу посчитать пока нельзя, достаточно `convexity` у облигаций. Монитор построит второй порядок сам: доходность = ставка + спред, Δy — DV01-взвешенный сдвиг кривой, отсюда ½·MV·C·(Δy + Δs)². Кросс FX он посчитает из DV01, CS01 и валюты позиции. Для IRS, XCCY и CDS без матрицы второй порядок будет нулевым, поэтому матрица заметно улучшает сценарии свопов.

**Проверка (публикация).** Неизвестный фактор, кривая, которой нет в прогоне, неверный бакет или валюта без курса — ошибка: прогон не публикуется. Одна и та же пара с разными значениями — ошибка при вставке.

**Как используется:**
- сценарии в мониторе (`docs/SCENARIOS.md` §2) — компоненты «Выпуклость» и «Кросс FX»;
- исторические сценарии — ранжирование окон с учётом второго порядка;
- колонки «Гамма ставок» и «Гамма спреда» и карточка позиции;
- в `window.DESK` по каждой позиции: `gamma`, `gammaIr` (к параллельному сдвигу всех кривых, RUB/б.п.²), `gammaCs`, `gammaIrCs`, `gammaSource` (`matrix` / `convexity`).

#### 4.3.4 PnL за день и его объяснение — `position_pnl`

| Компонента | Что это (ожидаемая методика) |
|---|---|
| `carry` | купонный / процентный доход за день. Облигации — начисление по доходности; IRS — (float − fixed) × номинал / 365 со знаком стороны; CDS — running premium |
| `rolldown` | эффект старения по кривой при неизменном рынке |
| `rates` | Σ по `position_risk` (DV01 × `move_bp` соответствующей точки). UI сверяет это поле с `risk × move_bp` в матрице «Rates explain»: используйте те же сдвиги, что и в `mkt_curve_point.move_bp` |
| `spread` | CS01 × изменение спреда эмитента за день |
| `fx_gross` | переоценка самой позиции из-за изменения курса |
| `fx_funding` | доля FX-переоценки **валютного фондирования** книги, отнесённая на эту позицию (см. 4.4.1) |
| `convexity` | эффект второго порядка за день: ½·Γ·Δ² по фактическим сдвигам дня (`move_bp` кривых, изменения спреда) — те же гаммы, что в `position_gamma` |
| `new_trades` | PnL сделок дня (цена сделки → закрытие) |
| `other` | всё, что объяснено, но не попадает в категории выше (купоны, амортизация, …) |
| `official` | **официальный** PnL позиции (бэк-офис / система учёта). Если его ещё нет — `NULL`: тогда unexplained = 0, а SDK пишет предупреждение |
| `break_note` | текстовая причина расхождения, если известна |

Монитор считает сам:
- `explained` = сумма девяти компонент;
- `unexplained` = `official − explained`;
- `fx` = `fx_gross + fx_funding`.

Пороги «разрыва», которые подсвечивает UI: |unexplained| ≥ 0,5 млн (внимание) и ≥ 2 млн (крит.) по книге. В Scenario Lab порог равен max(2 млн, 5 % от |official|).

### 4.4 Фондирование — `funding_deal`, `funding_pnl`

| Поле | Обяз. | Описание |
|---|---|---|
| `deal_id`, `book_id` | да | сделка и книга, которую она фондирует |
| `type` | да | `РЕПО с ЦК`, `TSY FTP`, `Обратное РЕПО`, `FX-своп`, `Гарантийное обеспечение` (свободный текст, UI группирует) |
| `ccy`, `amount` | да | валюта; сумма в валюте, `<0` привлечение |
| `rate` | да | текущая эффективная ставка, % (с учётом спреда) |
| `rate_expr` | нет | формула для показа: `RUONIA + 0.20%` |
| `start_date`, `maturity` | да* | `maturity` обязательна (лестница сроков) |
| `counterparty`, `collateral` | нет | |
| `pnl.carry` | да | стоимость или доход за день, RUB (`amount_rub × rate / 365` для простых сделок) |
| `pnl.fx_gross` | да для валютных | FX-переоценка сделки за день, RUB |
| `pnl.fx_allocated` | да для валютных | часть `fx_gross`, разнесённая на позиции книги (= Σ их `fx_funding`) |

Монитор считает сам:
- `amount_rub` = `amount × rate(ccy)`;
- `fx_delta` = `amount` для нерублёвых сделок;
- `tenor_y`;
- нераспределённый остаток `fx = fx_gross − fx_allocated` (показывается строкой фондирования книги);
- итоги `fundingPnl` и `fundingPnlByBook`.

#### 4.4.1 Разнесение FX-переоценки валютного фондирования

Чтобы книга видела FX-риск нетто (облигация в CNY на CNY-РЕПО почти не даёт FX-PnL), переоценка валютного привлечения разносится на позиции **той же книги**:
- берутся позиции с FX-дельтой противоположного знака в этой валюте;
- переоценка делится пропорционально |FX-дельте|;
- если таких позиций нет, вся сумма остаётся остатком сделки (`fx_gross − fx_allocated`).

Эталонная реализация — `allocateFundingFx` в `prototypes/desk-util.js`. Расчётный сервис может применить свою методику, но инварианты должны сохраняться:
- Σ `position_pnl.fx_funding` по книге = Σ `funding_pnl.fx_allocated` по книге. Иначе SDK пишет предупреждение.
- `fx_allocated ≤ fx_gross` по модулю.

### 4.5 Сценарии

**Определения** (`scenario_def`, глобально, `upsert_scenarios` или `scenarios` в пакете). Формат шока:

```json
{
  "scenario_id": "keyhike",
  "name": "Повышение КС +200 б.п.",
  "definition": {
    "curves":  { "RUB OFZ": [200,190,170,140,100,80,60,50,40,35,30], "RUB KEY": 150 },
    "fx":      { "USD": 15, "CNY": 15, "EUR": 15 },
    "spreads": { "_all": 25, "_mult": 2, "AA-": 50, "Самолёт": 300, "includeGov": false }
  }
}
```

- **`curves`** — сдвиг в б.п.: число задаёт параллельный сдвиг, массив из 11 значений — сдвиг по бакетам.
- **`fx`** — изменение курса в %; + значит ослабление рубля.
- **`spreads`** — правила спред-шока:
  - `_all` — сдвиг всех спредов, б.п.;
  - `_mult` — множитель к текущему спреду;
  - ключ-рейтинг или ключ-эмитент — сдвиг для этого рейтинга или эмитента, б.п.;
  - `includeGov` — шокировать ли «Гос» полностью; по умолчанию к нему применяется 35 % шока.

**Результаты.** Без полной переоценки (по умолчанию) UI сам считает сценарий в браузере разложением до второго порядка:
- Σ key-rate DV01 × шок, CS01 × Δспред, FX-дельта × Δкурс (с разнесением фондирования);
- **второй порядок**: матрица `position_gamma` или выпуклость;
- **кросс FX**: валютная часть PnL по шокированному курсу.

Это быстро и позволяет крутить шоки в Scenario Lab. Точность по тестам против точной переоценки — 0,03–0,25 % MV до ±500 б.п. по доходности. За этой границей сценарий помечается «нужна полная переоценка» (`docs/SCENARIOS.md`).

**Полная переоценка (необязательно).** Если либа умеет переоценивать портфель под шок, пишите результат в `scenario_result` (по позициям: `rates`, `spread`, `fx_gross`, `fx_funding`, `convexity` — второй порядок и прочая нелинейность по ставкам и спредам, `fx_cross` — кросс-эффект курса, `total` — полная переоценка) и `scenario_funding_result` (FX-остаток фондирования по книгам).
- Для **неизменённых пресетов** UI покажет полную переоценку; в Scenario Lab будет пометка «Полная переоценка (расчётный сервис)».
- Если пользователь поменял шок в редакторе, UI вернётся к оценке по чувствительностям.
- Для стрессов уровня «2022» полная переоценка заметно точнее, поэтому её стоит считать хотя бы для `stress22` и `rubdep`.

### 4.6 История итогов — `desk_history`

Графики «PnL за 22 дня», спарклайны DV01, CS01 и PnL берутся отсюда.
- При публикации **EOD**-прогона строка за `as_of` пишется **автоматически**: Σ official и explained позиций плюс фондирование (carry + FX-остаток), Σ DV01, Σ CS01.
- Для старта можно загрузить прошлые дни без детализации: `history: [{as_of, pnl_official, pnl_explained, dv01, cs01}]` в пакете или `writer.load_history()`. Дни, по которым есть опубликованный EOD, при этом не перезаписываются.
- Для текущего прогона (в том числе интрадей) последняя точка истории всегда берётся из него самого.

### 5.3 Проверки при публикации

**Ошибки** — прогон получает статус `failed` и не виден в UI:
- нет ни одной позиции;
- книга, кривая или бакет не из справочника прогона (внешние ключи; падает уже при вставке);
- `issuer` позиции не загружен в `run_issuer`; BOND или CDS без эмитента;
- нет курса для валюты, которая встречается в позициях, FX-дельтах, фондировании или кривых;
- у кривой не все 11 точек;
- дубликаты `position_id` или `deal_id` внутри прогона;
- неверные перечислимые значения (`instr_type`, `segment`, `kind`, `coupon_type`, `run_type`);
- гамма: неизвестный фактор, кривая не из прогона, неверный бакет, валюта без курса; одна пара с разными значениями.

**Предупреждения** — пишутся в лог прогона (`calc_run_log`, `/api/v1/runs/<id>`), прогон публикуется:
- Σ `position_risk` ≠ `dv01` больше чем на 0,1 % (и больше 100 ₽);
- у позиций нет PnL или нет официального PnL;
- Σ `fx_funding` по книге ≠ Σ `fx_allocated` по книге.

## 7. Эксплуатация

**Ежедневный цикл:**

1. После закрытия рынка расчётный сервис собирает статику и рынок, считает позиции и пишет EOD-прогон (SDK или `tdm import`).
2. Публикация мгновенно видна всем пользователям: страницы берут последний прогон при открытии или обновлении (F5).
3. Интрадей: те же шаги с `run_type="INTRADAY"`, хоть каждый час. Если официального PnL ещё нет, `official = NULL`.
4. Пересчёт дня: новый прогон с тем же `as_of`. Последний опубликованный вытесняет предыдущий, история `desk_history` обновляется.

**Обслуживание:**
- `python -m tdm runs` — последние прогоны и ошибки.
- `python -m tdm purge --keep-days 90 --keep-eod` — оставить все прогоны за последние 90 дат, по более старым только последний EOD. Неудачные прогоны удаляются; итоговая история остаётся.
- **Бэкап:** копируйте `data\tdm.sqlite` вместе с файлами `-wal` и `-shm`. Надёжнее остановить сервер или выполнить `sqlite3 tdm.sqlite ".backup backup.sqlite"`.
- **Объёмы:** ~10 000 позиций × ~4 точки риска ≈ 50 000 строк на прогон, порядка 10–20 МБ. SQLite спокойно держит годы таких данных.

**Версии контракта.** `contract_version` пишется в каждый прогон.
- Добавление необязательных полей не меняет мажорную версию: новые колонки получают `NULL`, старые UI их игнорируют.
- Переименование или смена смысла — новая мажорная версия: сервер будет поддерживать обе на переходный период.

## 8. Вне контракта: лимиты и VaR

Лимиты и VaR считаются отдельными модулями и в эту картину мира **не импортируются**:
- в контракте нет таблиц для них;
- из UI убраны все индикаторы загрузки, нарушения и VaR;
- пока их нужно смотреть в их собственных системах, параллельно с монитором.

Если позже понадобится собрать всё в одном окне, место для этого предусмотрено: отдельные таблицы `limit_def` / `limit_usage` и `var_result`, привязанные к тому же `run_id` или `as_of`, и отдельный загрузчик. Монитор при этом ничего не будет считать за эти модули — только показывать.

## 9. Чек-лист для расчётного сервиса

- [ ] `position_id` и `deal_id` стабильны между днями.
- [ ] Все суммы `*_rub`, DV01, CS01, JTD и PnL — в рублях; знаки по разделу 3.
- [ ] По каждой кривой все 11 точек: `rate` и `move_bp`.
- [ ] Σ key-rate DV01 = `dv01` позиции.
- [ ] Вторые производные: матрица `gamma` (минимум ставки×ставки и ставки×спред для облигаций и свопов) или хотя бы `convexity` у облигаций.
- [ ] `rates` в PnL = Σ (key-rate DV01 × `move_bp`) — с теми же сдвигами, что в `mkt_curve_point`.
- [ ] Курсы на все используемые валюты.
- [ ] Эмитенты всех облигаций и CDS — в `issuers`, с `issuer_group`.
- [ ] Разнесение FX-фондирования: Σ `fx_funding` = Σ `fx_allocated` по книге.
- [ ] `official` PnL — из официальной системы (или `NULL`, если ещё нет).
- [ ] EOD-прогон раз в день; при сбое — повтор (старые данные остаются видны).
